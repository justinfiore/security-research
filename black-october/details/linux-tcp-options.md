# Linux kernel: IPv4 TCP options use-after-free

**Last updated:** 2026-11-08 (America/New_York)

[Main Linux kernel summary](../black-october-2026.md#linux-kernel-ipv4-tcp-options-use-after-free) · [Main TOC](../black-october-2026.md#table-of-contents) · [Changelog](../../CHANGELOG.md)

**[CVE-2026-98432](https://www.cve.org/CVERecord?id=CVE-2026-98432) — kernel.org CVSS 3.1 9.8 Critical** is an IPv4 TCP race that can free socket options while they remain in use. kernel.org describes fixes in upstream and stable commits. Red Hat's public page, reread 2026-11-08, shows CVSS 3.1 9.8 with status VERIFIED. The earlier label, preliminary and subject to review, is no longer on the page. An earlier Red Hat draft scored 8.1 High with attack complexity High. On 2026-11-01 Red Hat released fixed kernels for RHEL 8, 9 and 10. Ubuntu still lists supported products without a released fix. On 2026-10-27 Anthropic reported that an unreleased Claude model produced a lab proof of concept which sends packets to a Linux server exposing a multipath TCP listener and runs commands as root, without credentials. Anthropic did not publish the exploit, and neither Anthropic nor the CNA reports in-the-wild use. Go's security team says the demonstrated exploit needs an MPTCP listener but the kernel bug is not MPTCP-specific, so disabling MPTCP is a fragile stopgap, not a fix.

**CISA KEV:** Not listed (catalog 2026.11.04, checked 2026-11-05). On 2026-11-03 Marcus Hutchins wrote that, as of 2026-11-02, residential proxies and RU-based VPNs were scanning port 443 with MPTCP and sending no HTTP data, and that he strongly suspects the scanning is for this flaw. He says there is no known public remote-code-execution exploit, and that the public proofs of concept are denial of service. He also says his own October 30 scan reached about 2,102,043 servers on port 443 over MPTCP, and about 762,774 that completed TLS, and that neither count separates patched kernels from unpatched ones. That is a researcher's scan report, not a confirmed compromise and not a KEV listing. Arista says it is not aware of exploitation in customer networks. AWS's November 4 bulletin says it has no evidence the issue has been leveraged. Absence from KEV is not evidence that exploitation has not occurred. [What KEV means](../black-october-2026.md#what-cisa-kev-means).

## Detection

1. `ss -Mlnp` lists sockets that are using MPTCP. Hutchins gives `sudo ss -Mlnp`. A listener there is the shape his suspected scanners are looking for. It is not proof the kernel is unpatched, and an empty list is not proof the IPv4 TCP bug is absent. He says `net.mptcp.enabled=0` does not change sockets that are already bound, so the process has to be restarted before `ss` is meaningful. Go 1.24 and later, including Caddy, bind MPTCP when the kernel allows it.
2. Inventory running Linux kernels and IPv4-facing TCP services; record the distributor package build rather than inferring status from the upstream version alone.
3. Check the distributor advisory for the exact installed kernel. The CNA record identifies affected ranges by commits, but distributors can backport fixes without changing the upstream version string.
4. Prioritize systems accepting untrusted IPv4 TCP connections. The CNA record describes races around retransmitted SYN processing and request-socket migration; package presence alone does not establish exploitation.

A default-order policy does not use that rule until the policy is recreated in strict order. The rule is not a kernel fix.

## Verification

- After a vendor update, confirm the booted package is the vendor-fixed build and that required TCP services function normally.
- Do not generate timing-sensitive malformed TCP traffic against production systems to test this vulnerability.

## Compromise response

The reviewed primary sources do not provide compromise indicators. Preserve kernel, crash and network telemetry if a suspected incident occurred, investigate adjacent service activity, and rebuild or rotate affected application credentials where host integrity cannot be established.
