# eMudhra / emSign: compromised intermediate CA keys

**Last updated:** 2026-10-30 (America/New_York)

[Back to eMudhra summary](../black-october-2026.md#emudhra--emsign) · [Changelog](../../CHANGELOG.md)

Eight P-384 intermediate CA keys were trivially recoverable: **six TLS and two code-signing keys**, with additional cross-signed certificates carrying the same keys. This is defective CA key generation, not a general break of TLS or proof that every eMudhra product was breached. Clients trusting these keys could accept fraudulent certificates even when their own servers use another CA.

**Priority:** inventory the software that *validates* certificates: outbound API clients, identity/JWKS fetchers, package managers, CI runners, update agents, TLS-inspecting proxies, and code-signature verifiers. For TLS impersonation an attacker also needs to intercept or redirect a connection; possessing a CA key does not by itself compromise every endpoint. Browser protection does not establish that a server-side application is protected.

**October 26 update:** do not reuse an early "fixed Java" table. Oracle's October 24 **[CVE-2026-114820](https://www.cve.org/CVERecord?id=CVE-2026-114820)** alert lists the earlier emergency builds as affected and requires a further root-removal update. CPython has now also released **3.15.2 / 3.14.10 / 3.13.18 / 3.12.16 / 3.11.18**, blocking the compromised keys in `ssl` (**[CVE-2026-115557](https://www.cve.org/CVERecord?id=CVE-2026-115557)**). See the [runtime inventory](#runtime-and-application-trust-store-inventory) and [verification limits](#verification).

**CISA KEV:** Not listed (catalog 2026.10.23, checked 2026-10-26). The CA compromise itself has no CVE; the related Go [CVE-2026-111943](https://www.cve.org/CVERecord?id=CVE-2026-111943), Java [CVE-2026-91403](https://www.cve.org/CVERecord?id=CVE-2026-91403) and [CVE-2026-114820](https://www.cve.org/CVERecord?id=CVE-2026-114820), and Python [CVE-2026-115557](https://www.cve.org/CVERecord?id=CVE-2026-115557) fixes are not listed. Absence from KEV is not evidence that exploitation has not occurred. [What KEV means](../black-october-2026.md#what-cisa-kev-means).

## Trust paths and what each mitigation changes

The original TLS intermediates are issued by `emSign Root TLS CA - G3`, which can chain through `emSign ECC Root CA - G3`. Sectigo's cross-signed copies of the same intermediate keys instead chain to **`AAA Certificate Services`** (also labelled **Comodo AAA Services root**). Code-signing consumers must additionally inspect trust in `emSign Root CS CA - G3`. Some stores trust the TLS/CS roots directly or have imported intermediates as anchors: checking only the common ECC root misses those cases.

| Mechanism | What it achieves | What it does not establish |
| --- | --- | --- |
| CA revocation (CRL/OCSP) | A verifier enforcing sufficiently fresh revocation information for the affected CA certificate can reject the path. | Publication is not delivery or enforcement. Leaf-only checks, stale cached CRLs, missing revocation pointers, soft-fail policies, and unreachable responders can leave acceptance paths. |
| Browser/platform pushed block | Reaches the verifier consuming OneCRL, CRLSets, or the platform's distrust data. | Does not update every PEM bundle, JDK, native extension, or SDK on that device. |
| Intermediate/key distrust in a verifier | Rejects affected certificate paths without depending solely on root-store updates. Key-based matching can cover cross-signs reusing that key. | A small hand-maintained list of certificate fingerprints is not equivalent to the vendor's complete fix. Encoding variations and verifier behavior matter; the Java guidance changed after the initial blocklist response. |
| Root removal | Prevents paths ending at the removed anchor and can protect clients without online revocation. | Removing the ECC root alone does not remove the AAA path, directly trusted TLS/CS roots, or locally imported anchors. It also breaks legitimate chains under the removed root. |

The disclosure site's [root identities](https://emudhra.we-have-a-problem.com/roots.json) and [intermediate identities](https://emudhra.we-have-a-problem.com/impacted-intermediates.json), together with [Bugzilla](https://bugzilla.mozilla.org/show_bug.cgi?id=2083449), are inputs for inventory, not a current per-device trust verdict. Match parsed certificate fingerprints/public keys and purpose constraints; a subject-name or filename search alone is only a lead. Root presence warrants investigation, but does **not** itself prove exploitability when another enforced policy blocks the keys. Absence from one bundle is not a whole-host clearance.

## Detection

1. Inventory **relying clients**, not only hosted certificates: browsers, OS stores, Java truststores, Python/application bundles, containers, Go executables, CI downloaders, mobile apps, and appliances. Record the effective trust source and update owner for each.
2. Compare stored/presented intermediate certificates with the SHA-256 fingerprints and issuer/serial pairs in the [incident description and comment 2](https://bugzilla.mozilla.org/show_bug.cgi?id=2083449#c2). Include Sectigo cross-signs; the original and cross-signed certificates have different fingerprints despite sharing compromised keys.
3. Names such as `EM DV TLS CA - G3B` are search clues, not identity checks. Cover DV/OV/EV TLS G3B/G3C and OV CS G3B/G3C; inspect alternate chain paths rather than just the first chain a server sends.
4. Read a saved public certificate on a clean analysis host without executing the source application:

   ```sh
   openssl x509 -in /mnt/snapshot/certificates/issuer.pem -noout -subject -issuer -serial -fingerprint -sha256
   ```

5. Inspect Go executable build metadata using the separate `stack-inventory.sh go /path/to/binary` companion script from a trusted environment. A patched compiler on the build machine does not establish the build version of a deployed executable.
6. Review historical TLS/proxy telemetry, certificate-transparency alerts for your domains, code-signing verification records, and downloaded artifact hashes. Unexpected issuers, certificate changes, or signatures warrant investigation; CT cannot prove that an unlogged certificate never existed.

**Impact assessment:** eMudhra says it issued no end-entity certificates from the affected intermediates. That does not prevent other holders of recovered keys from issuing them. Bugzilla comment 44 reports post-disclosure proof-of-concept certificates in CT; those counts were not independently reproduced here and do not establish real victim interception. Missing TLS/certificate telemetry leaves historical impersonation **unknown**.

### Runtime and application trust-store inventory

For each workload, privately record **deployed artifact/image digest, runtime vendor and full build, TLS library/backend, effective root source, custom overrides, revocation/block policy, and owner**. Include developer and CI downloaders, scheduled jobs, sidecars, serverless layers, embedded runtimes, and dormant recovery images. Do not publish customer inventories, internal destinations, truststore passwords, environment dumps, or private investigation results.

The paths and APIs below locate candidate trust sources; they are **not universal vulnerability checks**. Read configuration and resolved dependencies first. Runtime inspection should use a trusted installation, the same service account and launch options as the workload, and a controlled environment; do not execute a suspect application just to inventory it. Library examples from [Andrew Nesbitt's package investigation](https://nesbitt.io/2026/10/21/trust-stores-are-dependencies-too.html) and [Endor Labs' bundle investigation](https://www.endorlabs.com/learn/emudhra-intermediate-ca-compromise-the-trust-stores-you-patched-and-the-ones-you-didnt-know-you-had) are discovery leads from dated package samples, not claims that every current version remains affected.

#### Node.js and embedded JavaScript runtimes

- **Trust source:** standard Node distributions include bundled roots. Inspect `--use-bundled-ca`, `--use-openssl-ca`, `--use-system-ca` where supported, `NODE_OPTIONS`, `NODE_EXTRA_CA_CERTS`, `SSL_CERT_FILE` and `SSL_CERT_DIR` where applicable. An explicit TLS `ca` option or custom `SecureContext` can change the application's roots independently of defaults. `NODE_EXTRA_CA_CERTS` adds trust; it cannot remove an existing bad anchor.
- **Evidence to collect:** deployed Node version and distribution, the active CA mode, and actual `https.Agent`/Undici/TLS configuration. `tls.rootCertificates` describes bundled roots, not necessarily the effective set for every connection. Look for `rejectUnauthorized: false` and `NODE_TLS_REJECT_UNAUTHORIZED=0`; a bundle patch cannot compensate for disabled validation.
- **Remediation:** [Node's October 21 security release](https://nodejs.org/en/blog/vulnerability/october-2026-security-releases) confirms eMudhra `ca-cert` updates in **22.23.4 / 24.22.1 / 26.12.1**. Use those or later supported fixed releases and refresh separately selected OS/custom bundles. Do not infer an old/EOL line has a fix.
- **Bun:** [Bun 1.4.4](https://github.com/oven-sh/bun/security/advisories/GHSA-26q8-h657-pf84) removes the emSign root and rejects any chain containing one of the eight compromised keys; 1.4.3 and earlier accept them. Rebuild `bun build --compile` executables, which embed the runtime and trust store. Bun says `--use-system-ca` and `NODE_USE_SYSTEM_CA=1` do not help.
- **Electron and other embedders:** track the packaged runtime and each networking path separately. Updating the host's `node` executable does not replace an embedded Node or Chromium. Use the embedder's advisory rather than translating Node version numbers into an assumed product fix.

#### Java and Scala

- **Trust source:** inspect each vendor JDK/JRE, not just `java` on the administrator's `PATH`. Include `cacerts`, `jssecacerts`, `-Djavax.net.ssl.trustStore` and related type/provider settings, `jlink` images, bundled application keystores, and custom `SSLContext`/`TrustManager` implementations. JDK 8 commonly places its default store under `jre/lib/security`; later JDKs use `lib/security`. Paths may be symlinks to a distribution store.
- **Fresh remediation requirement:** the [October 21 Oracle alert](https://www.oracle.com/security-alerts/alert-cve-2026-91403.html) addresses intermediate distrust. The [October 24 alert](https://www.oracle.com/security-alerts/alert-cve-2026-114820.html) lists **8u511-b32 and the 11.0.33.0.2 / 17.0.21.0.2 / 21.0.13.0.2 / 25.0.5.0.2 / 27.0.1.0.2 builds as affected**, not as the final fix. [Current OpenJDK guidance](https://openjdk.org/emudhra) requires vendor release notes documenting **JDK-8395690 / CVE-2026-114820**, even if the runtime was updated in the previous few days. Exact replacement Oracle builds are in its linked support document; no unverified replacement version is asserted here. Temurin, Corretto, Zulu, Liberica and other distributions need their own current release/build evidence.
- **Root-removal workaround:** [Oracle's operational guidance](https://ops.java/emudhra) and OpenJDK currently name **four** roots: `emSign ECC Root CA - G3`, `AAA Certificate Services`, `emSign Root CA - G1`, and `emSign Root CA - G2`. The last two are a broader distrust policy, not evidence that their keys share the known weakness. Follow the vendor's backup, alias-verification, removal and restart procedure for every effective store; do not blindly copy aliases into an unrelated vendor store. Do not certify a hand-edited 16- or 48-fingerprint blocklist as equivalent to the current root-removal fix.
- **Distribution exception:** OpenJDK says Arch, Fedora, Gentoo, Oracle Linux and RHEL packages generally use OS certificates. **Debian/Ubuntu need a Java keystore rebuild**, not merely updated `ca-certificates` and `ca-certificates-java`: a [long-standing synchronization bug](https://bugs.debian.org/cgi-bin/bugreport.cgi?bug=1069251) can retain removed roots. Follow the [linked rebuild workaround](https://bugs.debian.org/cgi-bin/bugreport.cgi?bug=1142266) under change control, preserving any intentional custom anchors, and then check the resulting Java store. FreeBSD/Homebrew JDK packages require their own updates.
- **Revocation alternative:** the official guidance offers `-Dcom.sun.net.ssl.checkRevocation=true -Dcom.sun.security.enableCRLDP=true` for TLS and, on JDK 17+, `jarsigner -verify -revcheck -strict` for signed JARs. Validate network access, cached data and failure policy; these are not proof that every custom trust manager enforces revocation. Do not put keystore passwords in shared command transcripts.
- **Scala:** JVM Scala inherits the Java verifier. Include sbt, Mill, Coursier, scala-cli, SDKMAN installations and CI-selected JDKs, not only production services. Scala.js on Node follows the Node path; Scala Native needs its actual native TLS backend inventoried. The [Scala advisory](https://www.scala-lang.org/blog/jdk-certificate-vulnerability.html) provides ecosystem guidance, but its early fixed-build table must be read alongside the newer OpenJDK/Oracle root-removal requirement.

#### Python

- **Trust sources:** stdlib `ssl` uses its configured OpenSSL paths; `ssl.get_default_verify_paths()` identifies defaults and recognized environment overrides, not the roots in every custom `SSLContext`. Requests/httpx commonly use certifi; inspect `certifi.where()`, Requests' actual verification settings, `REQUESTS_CA_BUNDLE`, `CURL_CA_BUNDLE`, `SSL_CERT_FILE` and `SSL_CERT_DIR`. urllib3's caller can supply a different context/bundle. Distro packages may patch bundle selection.
- **Independent copies:** inventory each virtualenv/conda environment, pip's vendored certifi, ensurepip/virtualenv seed wheels, `uv`, AWS CLI/botocore fallback bundles (`AWS_CA_BUNDLE` or client `verify` settings), httplib2, gRPC native roots, macOS installer bundles, Lambda layers and packaged executables. Installing certifi in one environment does not refresh another program's embedded file.
- **Bundle/tool baselines:** the [Python security announcement](https://discuss.python.org/t/information-for-python-users-regarding-emudhra-emsign-ca-certificate-security-incident/109576) recommends **certifi 2026.10.19**, **pip 26.2.2**, **uv 0.13.4**, **sigstore 4.5.1**, **conda 26.9.4**, and **pixi 0.82.1**, or later fixed versions. It recommends certifi October 19 rather than October 18 for compatibility with unaffected roots. For standard upstream pip, OS roots and `--cert`/`REQUESTS_CA_BUNDLE` are not a reliable way to subtract trust from old vendored certifi. Follow the announcement's independently authenticated download/hash-verification approach when bootstrapping an update from an unpatched client; do not use `--trusted-host` or disable verification.
- **New October 26 runtime protection:** [CPython's release team](https://discuss.python.org/t/python-3-15-2-3-14-10-3-13-18-3-12-16-and-3-11-18-are-out/109678) confirms **3.15.2 / 3.14.10 / 3.13.18 / 3.12.16 / 3.11.18**, **CVE-2026-115557**, block the compromised intermediate keys in `ssl` (PSF CNA CVSS 4.0 9.4 Critical). The PSF CNA corrected its record on 2026-10-27 to branch-specific affected ranges that end before those releases. The team states normal pip use on those interpreters is protected even before pip is upgraded. **Still refresh bundles and pip**, because other consumers and older interpreters may use them. This does not promise coverage for native extensions that bypass Python's `ssl`, alternative interpreters, or disabled certificate verification.
- The October 26 releases have binary installers for **3.15.2 and 3.14.10**; **3.13.18, 3.12.16 and 3.11.18 are source-only**. Verify downstream package/image availability instead of assuming a new upstream release updated every deployment. This announcement supplies no new 3.10-or-older fix; require explicit distributor evidence or move to a supported fixed interpreter. Refresh newly created environments so stale seed wheels do not reintroduce old tooling.

#### PHP

- **Trust source:** inspect OpenSSL streams and ext-curl separately. `openssl.cafile`, `openssl.capath`, `curl.cainfo`, stream-context `cafile`/`capath`, and `CURLOPT_CAINFO`/`CURLOPT_CAPATH` can override defaults; libcurl's TLS backend matters. The [official `openssl_get_cert_locations()` API](https://www.php.net/manual/en/function.openssl-get-cert-locations.php) reports candidate locations. CLI, FPM and Apache can load different `php.ini` files and environment settings, so a CLI check alone is insufficient.
- **Bundled trust:** inspect Composer itself and installed `composer/ca-bundle`, plus SDKs such as stripe-php, braintree_php, gRPC and legacy Guzzle 3 for their actual selected CA files. `composer.lock` alone cannot tell whether an embedded PEM is loaded at runtime.
- **Remediation:** update the selected OS/custom bundle and affected library/tool. [composer/ca-bundle 1.6.0 release notes](https://github.com/composer/ca-bundle/releases/tag/1.6.0) confirm eMudhra distrust and `CaBundle::findDistrustedCertificate()` for known-bad certificates in PEM chains. The helper must actually be called and is not a universal TLS policy. No PHP-wide fixed interpreter version is asserted; patching PHP alone is not a substitute for checking these stores.

#### .NET / C#

- **Trust source:** the usual .NET X.509 path uses platform facilities: Windows certificate stores, Linux OpenSSL root locations, and Apple's trust settings on macOS. Microsoft's [cross-platform cryptography documentation](https://learn.microsoft.com/en-us/dotnet/standard/security/cross-platform-cryptography) describes the differences, including Linux `SSL_CERT_FILE`/`SSL_CERT_DIR` and fallback paths. Inventory the account-specific as well as machine store where applicable.
- **Overrides:** review `X509ChainPolicy.CustomTrustStore`/`TrustMode`, `ServerCertificateCustomValidationCallback`, `RemoteCertificateValidationCallback`, custom handlers, and NuGet/native dependencies with their own roots (including legacy native gRPC). An `HttpClient` test does not exercise every custom or native verifier.
- **Remediation:** refresh the actual OS/container trust data and custom stores, not just the SDK on the build host. Microsoft says its October 26 out-of-band Windows update removes seven affected certificates, and Edge received a Certificate Trust List update on October 27; verify the actual Windows/Edge state and do not apply that claim to Linux, custom or bundled stores. On Windows, inspect effective disallowed-certificate contents and update policy; a sync timestamp alone does not prove the required entries were received or enforced. Microsoft's documentation explicitly says the .NET **Disallowed store is not used for Linux chain building**: do not transplant a Windows workaround to Linux. No universal .NET fixed-version threshold is asserted. [Microsoft][msrc-response]

#### Go

- **Trust source:** `crypto/x509` commonly uses system roots, but inspect custom `tls.Config.RootCAs`/`ClientCAs`, `x509.CertPool`, bundled/generated roots, `SSL_CERT_FILE`/`SSL_CERT_DIR` on platforms that support them, and alternate TLS implementations. A custom verifier or `InsecureSkipVerify` path needs separate review.
- **Remediation:** [GO-2026-6809](https://pkg.go.dev/vuln/GO-2026-6809) identifies **1.26.10 / 1.27.3** as fixed for `crypto/x509.Certificate.Verify`. Rebuild and redeploy **each executable** using those or later supported fixed toolchains; compiler installation does not patch old binaries. Read deployed build metadata with a trusted `go version /path/to/binary` or the inventory companion. Vendor backports need advisory evidence if their version string differs.
- Update the runtime image's OS bundle too, including copies placed into `scratch`/distroless images. A new Go test program's rejection proves something about that program's verifier, not that every old executable or CA file in the image is fixed.

#### Ruby

- **Trust source:** Ruby/OpenSSL and Net::HTTP commonly use OpenSSL's default paths, but each client can supply `ca_file`, `ca_path` or a constructed `OpenSSL::X509::Store`. Inspect `SSL_CERT_FILE`/`SSL_CERT_DIR`, the linked OpenSSL installation and the actual service account. On macOS, do not equate Apple's framework block with protection for a Ruby using `/etc/ssl/cert.pem`.
- **Bundled trust:** the published package investigation found Stripe and httpclient building their own stores, Excon adding bundled roots alongside system roots, Honeybadger and aws-sdk-v1 selecting bundled files, gRPC providing native roots, and aws-sdk-core optionally using a bundle through `Aws.use_bundled_cert!`. Check your installed version and selected path rather than treating every gem as having identical behavior.
- **Remediation:** update the bundle-owning gem or explicitly configure the client to use a maintained verified store. Candidate controls include Stripe's `ca_bundle_path`, httpclient's `ssl_config.set_default_paths`, Excon's `ssl_ca_file`, and `GRPC_DEFAULT_SSL_ROOTS_FILE_PATH` where supported. Verify whether a setting **replaces or adds to** the existing roots. No blanket Ruby/gem fixed-version table is asserted without current maintainer evidence.

#### Rust

- **Trust source:** inspect the resolved `Cargo.lock`, features and deployed binary. `native-tls` delegates to its platform backend; `rustls-native-certs` loads platform roots for rustls; `webpki-roots`/`webpki-root-certs` supply bundled data compiled into the application. A custom `RootCertStore` or certificate verifier changes that picture. Libraries such as reqwest can select different backends/features between builds.
- **Verified baselines:** [RUSTSEC-2026-0381](https://rustsec.org/advisories/RUSTSEC-2026-0381.html) and [RUSTSEC-2026-0383](https://rustsec.org/advisories/RUSTSEC-2026-0383.html) require **1.0.10 or later** for the respective root-data crates. Both advisories mark **0.26.11** as a compatibility wrapper without its own store: its separately resolved **1.x parent must be at least 1.0.10**. Do not label every 0.26.x occurrence equally or stop at the wrapper's version.
- [RUSTSEC-2026-0382](https://rustsec.org/advisories/RUSTSEC-2026-0382.html) gives `rustls-webpki` fixed ranges **`>=0.103.16, <0.104.0-alpha.1`** and **`>=0.104.0-alpha.8`**, rejecting paths containing the compromised public keys. A loose `>=0.103.16` comparison misses the affected prerelease range.
- Refresh resolved transitive dependencies, rebuild and redeploy affected binaries, and update the OS store for native-root paths. RustSec/cargo-audit findings are useful dependency evidence, not proof of the effective trust policy in an already deployed binary. Updating `rustc` alone does not replace compiled-in crates or roots.

### Containers, OS stores and alternate copies

- **Images are separate machines for trust purposes.** Patch/rebuild both build and runtime stages, pull the intended fixed base digest, invalidate stale package-install layers, and redeploy running instances. A new host package, mutable tag, or CI compiler does not change an existing image or process. Include sidecars, init containers, copied JDKs, mounted bundles, secrets/config maps, serverless layers and native libraries. Pinned/EOL images may never receive upstream rebuilds; require explicit maintained-package evidence rather than assuming they are safe.
- **OS packages:** [Debian DSA-6572-1](https://lists.debian.org/debian-security-announce/2026/msg00487.html) fixes trixie `ca-certificates` in **20250419+deb13u1**, removing both emSign G3 and Comodo AAA. [Ubuntu USN-8944-1](https://ubuntu.com/security/notices/USN-8944-1) specifies **20260816ubuntu0.22.04.1 / 20260816ubuntu0.24.04.1 / 20260816ubuntu0.26.04.1 / 20260816ubuntu0.26.10.1** for the corresponding releases; its notice describes emSign removal and a bundle refresh, not proof about every separately configured AAA copy. Java needs the additional Debian/Ubuntu step above. Use distro version comparisons and backport records, not upstream-only numeric comparisons.
- **RHEL/UBI/OpenShift:** [RHSB-2026-012](https://access.redhat.com/security/vulnerabilities/RHSB-2026-012) tracks **[CVE-2026-114406](https://www.cve.org/CVERecord?id=CVE-2026-114406)**, links RHEL 8/9/10 errata, and includes RHEL 6/7 in its affected list. The Red Hat CNA record (updated 2026-10-26) now marks RHEL 7 ELS fixed from `ca-certificates-2026.2.92_v9.0.319-70.3.el7_9` and scores the issue CVSS 3.1 6.8; RHEL 6 and OpenShift 4 remained affected with no fixed version. It provides platform-specific mitigation links and directs customers to rebuild dependent images. Treat other distro branches, Alpine, Amazon Linux, Bottlerocket, Azure Linux and appliance images as **unverified here** until their current advisory and the deployed artifacts are checked; October 24 "no patch yet" claims are not carried forward as October 26 facts.
- **macOS:** [Apple's incident guidance](https://support.apple.com/en-us/149555) separates its automatically blocked framework path from tools using `/etc/ssl/cert.pem` and apps with independent roots. Its 2026-10-29 version names **curl, git, python3, ruby, perl and openssl** from macOS or the Xcode Command Line Tools as using that file without Apple's block or revocation checks; Apple says a future macOS update will fix it, and none was listed on 2026-10-30. Until then those tools can still accept the affected certificates. Follow Apple's administrator workaround only with backups and availability review: it removes `emSign ECC Root CA - G3`, and optionally `AAA Certificate Services` for the Sectigo cross-signs, which can break other sites that chain to those roots; a macOS update can restore the edited file, so re-run Apple's check after each update. Third-party Python, Homebrew or other tools with their own bundles are outside this file; use their own updates (for Python, see [above](#python)). Separately, upstream curl's Mozilla-derived [`cacert.pem` extract dated 2026-10-20](https://curl.se/docs/caextract.html) no longer contains `emSign ECC Root CA - G3`; `emSign Root CA - G1` remains and `AAA Certificate Services` is absent from both it and the previous 2026-09-25 extract (compared for this guide on 2026-10-30).
- **Static inspection limits:** parse every certificate in a PEM bundle, not just the first one. Inspect JKS/PKCS#12 stores with appropriate read-only tooling; scan extracted package/image contents, not just filenames. `grep emSign` against base64 PEM data or a listing of `/etc/ssl/certs` cannot certify absence. Missing/unreadable paths, hashed symlinks, compiled-in anchors, conditional fallback bundles and custom verification code are coverage gaps, not "clean" results. Package scanners can miss CA data that is not declared as a dependency.

## Remediation

1. Update OS/browser/application trust data using each distributor's supported channel. Confirm intermediate blocking or the relevant root removal is actually enforced; a generic CA-bundle update may not incorporate OneCRL or cover cross-sign paths.
2. Deploy the Firefox/ESR fixes above or later supported releases, including the Android 158.0.2 follow-up. Update NSS consumers separately; Firefox's remotely delivered OneCRL is not a global operating-system revocation list.
3. Rebuild and redeploy Go programs with **1.27.3 / 1.26.10 or a later supported fixed toolchain**. Obtain an explicit backport statement for vendor builds; refresh images and replace old running processes as well as build caches.
4. For opaque appliances, pinned CA bundles, Java stores, and custom TLS libraries, require vendor confirmation covering affected keys and alternate chains. **Cisco:** check each product in [cisco-sa-emudhra-info-ScS22A1r][cisco-sa]. It links remediation steps (for example Secure Firewall ASA/FTD/FMC and ISE guidance, Trusted Root 2.8 for Secure Email products via `updatenow` when updates are manual), lists software fixes with target dates for products such as ISE, IOS XR, NSO and RoomOS, and lists products still under investigation, including IOS XE, Nexus 3000/9000 and MDS 9000 trains. Cisco says the advisory is interim and that products not listed are not affected per its review; recheck it rather than treating a target date as a shipped fix. Splunk products are covered in a separate Splunk advisory linked from it. If protection cannot be established, restrict sensitive outbound operations or apply an approved targeted distrust policy pending an update. Never disable TLS verification to restore service.
5. Replace any deployed certificate whose chain is affected by compromise or resulting distrust, using a verified unaffected hierarchy. eMudhra's October 22 update offers Sectigo replacements through CertiNext or support. Inspect the **actual replacement chain**; a CA brand alone is not evidence of safety.
6. Preserve public certificates and relevant logs before changes. Do not import a compromised intermediate as a trust anchor to make an application work. Do not assume cached CRLs, leaf-only OCSP checks, or successful HTTPS requests establish protection.

**Server-certificate availability deadline:** [Google](https://blog.google/security/protecting-chrome-and-android-users-from-compromised-emudhra-intermediate-ca-certificates/) asks operators with certificates chaining to `emSign ECC Root CA - G3` to install replacements from another accepted hierarchy before its expected **October 27 morning PDT** root-store rollout. Legitimate certificates under unaffected intermediates can still break when their root is removed. Stage replacement-chain tests now; do not restore a distrusted root as an outage workaround.

### Central controls, CT and egress limits

| Control or observation | Useful role | Required limit |
| --- | --- | --- |
| TLS-inspecting egress proxy or gateway | A patched upstream verifier can reject bad chains for traffic it actually terminates and validates. | CONNECT pass-through, bypass routes and uninspected destinations do not inherit that verification. Validate both app-to-proxy and proxy-to-origin authentication. A gateway does not protect an already impersonated first hop. |
| FQDN/SNI allowlists, DNS policy, NAT and L3/L4 firewalls | Constrain destinations and reduce unrelated egress exposure. | A forged certificate can impersonate an **allowed** hostname. Routing/NAT and name allowlisting do not themselves validate the server's certificate. |
| WAF, CDN, load balancer and reverse proxy | A proxy can be a TLS client toward an origin; its upstream trust store deserves review. | An inbound WAF rule does not patch an application's outbound TLS. A backend mode that never validates certificates is not a mitigation; assess its separate authentication risk. Managed services need product-specific evidence, not an assumption that all vendors patched. |
| mTLS/client-certificate authentication | Review uploaded trust stores and authorization mapping on gateways, proxies and applications. | Do not accept arbitrary publicly rooted client certificates as sufficient identity. Private-CA-only deployments need their own assessment; public WebPKI distrust does not automatically alter uploaded mTLS stores. |
| Passive certificate/issuer telemetry | Can help identify affected chains where certificate messages are visible, such as full TLS 1.2 handshakes. | TLS 1.3 encrypts certificate messages; resumed sessions and incomplete captures also limit visibility. Flow logs generally give addresses/ports, not complete hostnames or chains. Prefer endpoint or terminating-proxy telemetry; subject-text IDS matches are not cryptographic identity checks. |
| CT monitoring and CAA | Useful detection and issuance-governance controls for your domains. | CT absence is not proof of no interception for clients not enforcing CT. CAA constrains compliant issuance, not an attacker already holding a CA key. Neither replaces distrust. |

Google states no TLS certificates under the six intermediates were logged to CT before its blocking action and limits its historical protection claim to **CT-enforcing clients**. This must not be generalized to all server-side clients, all Android apps, or later proof-of-concept issuance.

For concrete vendor procedures, [Cloudflare's response](https://blog.cloudflare.com/emudhra-certificate-compromise) distinguishes WARP/One Client, cloudflared, origin validation, uploaded mTLS CAs and opt-in container HTTPS egress interception. [Unit 42](https://unit42.paloaltonetworks.com/emudhra-certificate-compromise/) provides PKI discovery, egress/proxy and identity-log hunting guidance. [Fleet](https://fleetdm.com/guides/find-and-fix-emudhra-intermediate-ca-exposure) covers endpoint policies and its own osquery CA bundle; [Endor Labs](https://www.endorlabs.com/learn/emudhra-intermediate-ca-compromise-the-trust-stores-you-patched-and-the-ones-you-didnt-know-you-had) covers hidden-bundle discovery and scanner limits. Some linked scripts **change systems** and require separate approval/testing; linking them is not a recommendation to run their remediation automatically or to accept a simplistic PASS result.

## Verification

- Record each deployed trust-store package/build, update time, effective bundle path, running application version, and verification owner. Include embedded/offline copies and custom settings that disable updates.
- In an isolated test environment, use approved known affected certificate-chain fixtures with the **same verifier and policy as production**. Require rejection of affected original and cross-signed paths; a random expired certificate failing is not a meaningful test of the new block.
- Run an unaffected valid-chain control and confirm hostname verification remains enabled. For code-signing consumers, test their signing-policy trust separately from TLS; timestamp and signature policy may differ.
- Verify rebuilt Go artifact metadata on the deployment itself, restart/redeploy, and confirm traffic comes from the new instances. Updating `go` alone is insufficient.
- Check that replacement server chains work for supported clients without restoring distrusted anchors. Record vendor evidence or an explicit **unknown** for clients you cannot test.
- Revocation at the CA is not proof that every client fetched or enforced it. The source record also raises CRL availability and caching concerns; this guide does not certify current CRL/OCSP reachability or universal trust-store coverage.

### Java: use the official offline checker, with its actual limits

[OpenJDK's `CheckCerts.java`](https://cr.openjdk.org/~mr/CheckCerts.java), linked by both OpenJDK and ops.java, works on **JDK 8 and later**. Retrieve and review the source through a trusted channel, retain its license, and run it with the application's actual JDK and default-truststore settings. On JDK 11+ the downloaded source can be launched with `java CheckCerts.java`; on JDK 8 compile it with a trusted compatible `javac`, then run `java CheckCerts`. A JRE-only image needs a compatibly compiled class rather than source-launch assumptions. The checker itself makes **no network requests** and does not modify trust configuration.

As read on October 26, it initializes the default `TrustManagerFactory` with a null keystore and examines accepted issuers for subject-name substrings matching the **four roots** in the current Java guidance. It prints `BAD ROOT` and exits **1** on a match; otherwise it prints `No bad root certificates found` and normally exits **0**. An initialization/runtime error is an error, not evidence of safety.

**It is a targeted root-presence check, not an exploitability verdict:**

- It does not attempt a TLS handshake, inspect `blocked.certs`, prove revocation enforcement, or compare cryptographic fingerprints. A name match needs certificate identity confirmation.
- A runtime retaining a named root while enforcing a key block can still print `BAD ROOT`; this does not cancel the current vendor recommendation to apply the subsequent root-removal update.
- It does not enumerate all files or see an application-created trust manager, a separately supplied `SSLContext`, every provider, embedded native TLS, code-signing policy, or directly trusted roots/intermediates outside its four-name list. Running it under different flags/user/provider settings changes what it checks.
- A zero result is evidence only about the default trust-manager accepted-issuer list examined in that process. Combine it with current vendor-build evidence, custom-store review and application-path tests.

### Optional application-path tests: no universal PASS

Use approved offline fixtures where possible. If external testing is explicitly approved, the [disclosure site](https://emudhra.we-have-a-problem.com/) documents public TLS test hosts, including `https://dv-g3b-emudhra.we-have-a-problem.com/` and `https://dv-g3b-aaa-emudhra.we-have-a-problem.com/` for two different paths. These two examples do not cover every TLS key, encoding variant, directly trusted anchor or code-signing policy. Use the actual application verifier, supply no credentials/client secrets, set timeouts, avoid redirects, and do not install its certificates as trusted roots. Network tests disclose at least connection metadata to the remote service and are not run by this guide.

| Observed result | Interpretation |
| --- | --- |
| Successful TLS validation **and confirmation that the peer chain uses an affected key** | Demonstrates acceptance on that tested path/configuration. HTTP status alone is insufficient if a proxy terminates TLS, a redirect changes peers, or the test site's chain has changed. |
| Rejection attributable to the affected key/root or verified chain policy, with an unaffected valid-chain control succeeding | Evidence that this fixture is rejected by this verifier under the recorded configuration. It does not prove rejection of all alternate paths or encodings. |
| Generic `SSLException`, handshake alert, expired/mismatched fixture, unreadable CA file, DNS failure, timeout, proxy denial or failed positive control | **Inconclusive/error**, not "protected". Record the precise cause and fix the test conditions before claiming a security result. |

In particular, catching every Java `SSLException` (or Ruby SSL error/.NET authentication exception) as "OK (rejected)" can confuse protocol, network and configuration failures with successful distrust. Do not carry forward that classification or old private test results. This page adds no universal scanner and claims **no live vulnerability tests of the reader's systems**.

## Compromise response

- CA-key compromise alone does **not** demonstrate theft of your leaf private key, stored passwords, or past TLS session keys. Avoid claiming passive decryption of all recorded traffic; assess actual interception and endpoint exposure.
- If fraudulent certificates or interception are suspected, preserve certificate chains, timestamps, destination/DNS/proxy logs, downloaded binaries, and relevant authentication records. Investigate the network path and affected endpoints before returning them to service.
- From a clean client with verified trust, revoke tokens, API keys, passwords, and sessions that may have traversed impersonated services. Replace local private keys if endpoint compromise exposed them; rotate application signing/session secrets where downstream takeover is plausible.
- For suspicious signed software, quarantine the artifact, compare with independently authenticated publisher hashes/provenance, and rebuild compromised hosts. A valid signature under an affected chain is not sufficient publisher authentication.
- Review identity-provider and service audit logs for misuse after the suspected interception, invalidate attacker-created sessions/keys, and assess notification obligations. Trust-store remediation prevents future acceptance; it does not undo actions taken with already stolen credentials.
